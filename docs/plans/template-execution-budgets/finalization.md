## Optimization experiments

The owner's follow-up asks to compare preallocation and other strategies. Prioritize removing repeated admission work, then measure the remaining output cost. The reviewed metered-live allocation profile attributes 83.21% of sampled allocation bytes to `newParseAdmission`, `prepareSource` and `admitCached`; this is allocation attribution, not an estimate of execution time saved. CPU profiles also identify checkpoint and writer dispatch costs. The short serial heap/contention profiles do not establish retained-memory or concurrency behavior.

| Strategy | Controlled comparison | Tradeoff and required controls | Owner |
| --- | --- | --- | --- |
| Small inline admission storage | Existing maps versus lazy maps versus inline capacities 4, 8 and 16 with overflow indexing | Can remove common-case allocations; increases each runtime's size and reset cost. Measure threshold boundaries K-1/K/K+1 and graphs of 1/4/16/64 templates. Inline does not imply stack allocated. | 3 |
| Immutable compiled metadata | Repeated graph traversal versus summaries computed at compilation | Moves work to compilation and increases cache size. Preserve unique accounting, all-path depth, tighter callers, dynamic loads, cycles and development invalidation. Avoid quadratic transitive-closure storage. Include cold compile and retained cache cost. | 3 |
| Lazy input bookkeeping | Eager bookkeeping versus allocation only when accepted data requires it | Empty/scalar inputs should not pay unnecessary map costs; mutable input must still be copied and every capability checked. Include nil, scalar, nested, shared and cyclic inputs. | 3 |
| Consolidated output dispatch | Current adapter/check stack versus one canonical accounting boundary | Targets CPU cost that admission preallocation cannot remove. Preserve post-escape byte counts, cancellation, callback reentrancy, short writes, first causes and transactions. | 2 |
| Small output reserve | Natural buffer growth versus capped initial reserves such as 256 B, 1 KiB and 4 KiB, or a bounded compiled size hint | Helps only if growth/copying remains material. Measure empty/tiny results, escaping, 8/64 KiB results, failures and discarded transactions. Capacity choices are experiments, not selected defaults. | 2 |
| Reuse of scratch with retention limits | No additional pooling versus reuse only for surviving allocation hotspots | Clear request references, drop oversized storage and measure cleanup cost. Results must never alias recycled buffers. A per-entry capacity cap is not a global memory bound; include concurrent load, large-then-small traffic and cold/post-GC runs. | 2/3 |

Do not reserve the configured maximum output/value/input allowance up front. A quota is an upper bound, not predicted demand; preserve existing logical charging and reservation-before-construction rules. Start with compact admission state and lazy bookkeeping, independently evaluate immutable metadata and output consolidation, then test buffer sizing or pooling only where the resulting profiles justify it. Keep one production implementation and internal measured thresholds; do not add caller tuning options for these experiments. Go's [Pool contract](https://pkg.go.dev/sync#Pool) permits automatic eviction, so correctness and acceptable cold behavior cannot depend on reuse. The [GC guide](https://go.dev/doc/gc-guide#Eliminating_heap_allocations) explains why allocation rate and retained heap must be evaluated separately.

Use focused paired experiments with fixed source/input hashes, toolchain, positive quotas and output ownership; change one factor at a time before checking the combined candidate. Lane 4 records each tested variant, accepted/rejected verdict, time/allocations/bytes, live heap/RSS and relevant profile evidence in the existing report. Include serial and concurrent behavior, p50/p99 and minimum/current Go compatibility. Screen variants on the affected workloads, then run the full representative program on the selected combination; do not multiply the entire release matrix by every capacity. No capacity is selected and no performance improvement is claimed until measurements support it.
